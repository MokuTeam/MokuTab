# Changelog

All notable changes to MokuTab, called WorkatoMCP before 2.0. Versions refer to the published npm packages `@mokuhub/mokutab-bridge` (the local bridge) and `@mokuhub/mokutab-shared` (tool schemas); up to 1.13.0 they were published as `workatomcp-bridge` and `workatomcp-shared`. The Chrome extension is versioned alongside them, and each GitHub release carries it as a CI-built zip.

This project follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) conventions. Dates are the commit dates of the corresponding release.

## Unreleased

### Fixed

- **Leased tabs stayed open** ([#3](https://github.com/MokuTeam/MokuTab/issues/3)). Agents that never called `chrome_release_tab` left their tabs behind, for three reasons, each fixed:
  - Leases lived in memory only, so a bridge restart forgot them and nothing ever closed their tabs. The bridge now saves them in its state dir (`leases.json`). After a restart, the tab of each saved lease is closed when its profile reconnects, provided Chrome has not restarted in between: tab ids start over with Chrome, so the extension now sends the bridge an id for its Chrome session on connect, and a lease from another Chrome session is dropped without closing anything. An adopted tab (`adopt_tab_id`) is never closed this way.
  - An MCP session that ended kept its leases until the 30-minute sweep. Now the end of a session (an HTTP DELETE, a dropped SSE stream) releases them: the tabs they opened close and adopted tabs stay. A client that never ends its session, such as the stdio proxy, still relies on the sweep.
  - A call that named the leased tab by `tabId` did not count as use, so a script that leased once and then passed the tabId lost its tab to the sweep 30 minutes after leasing, even while working in it. Such a call, from any session, now keeps that lease alive.

### Added

- `MOKUTAB_LEASE_IDLE_MINUTES` sets how long an unused lease lasts (whole minutes, at least 1; 30 by default).

### Changed

- The `chrome_lease_tab` description says a lease also ends with its MCP session and that a call by `tabId` counts as use, so `schema_revision` changes.

## bridge 2.0.0 · shared 2.0.0 (2026-10-20): `@mokuhub/mokutab-bridge` and `@mokuhub/mokutab-shared`, formerly `workatomcp-bridge` and `workatomcp-shared`

WorkatoMCP is now **MokuTab**, a MokuHub product: browser tools for AI agents that drive the user's own logged-in Chrome. The code is split into a core and modules, and Workato is the first module, switched on and off in the extension popup. Upstream features this project never used are gone. Read **Breaking changes** and **Migration** before upgrading a 1.x machine.

### Breaking changes

- **New packages and commands.** `workatomcp-bridge` is now `@mokuhub/mokutab-bridge`, with the commands `mokutab-bridge` and `mokutab-stdio`; `workatomcp-shared` is now `@mokuhub/mokutab-shared`. The old packages get no further releases. The new package keeps the old command names as aliases until 3.0, so npm refuses to install it over the old package (`EEXIST`): uninstall the old one first, as [Migration](#migration) says.
- **Registration key `mokutab`.** Claude Code registers the bridge as `mokutab`, so tools read `mcp__mokutab__chrome_snapshot`. A registration under the old key `workato` reaches the same URL and keeps working until it is removed, but permission allowlists that name `mcp__workato__*` need the new prefix.
- **Four tools renamed.** `workato_list_profiles`, `workato_switch_profile`, `workato_bridge_info` and `workato_reload_extension` are now the core tools `chrome_list_profiles`, `chrome_switch_profile`, `chrome_bridge_info` and `chrome_reload_extension`, with the same parameters. The old names stay until 3.0 as aliases kept by the Workato module. While it is on, `tools/list` carries each one after every other tool, as a copy of the new tool's served schema described as "Old name of <tool>, kept until 3.0.", and a call runs the new tool: the router swaps the name before routing, so the pin, strict mode, leases and auto-file treat both names alike. While Workato is off the old names are not listed, and a call is refused naming the new tool; nothing is sent.
- **Workato is off on a fresh install.** A machine that never ran 1.x serves the 52 core tools until Workato is switched on in the popup. An upgrade keeps it on (see the module switch below).
- **Data dir `~/.mokutab`.** The first start moves `~/.workatomcp` there.
- **Environment variables `MOKUTAB_*`.** Each `WORKATOMCP_*` name is still read when its replacement is unset, until 3.0.
- **`@mokuhub/mokutab-shared` API.** The four renamed tools moved from `TOOL_NAMES.WORKATO` to a new `TOOL_NAMES.BRIDGE` family, and the record-replay, agent chat and echo-route exports listed under Removed are gone.
- **Removed tools.** The `flow.*` tools and the unlisted tools the bridge used to forward by name are gone (see Removed). `chrome_read_page` no longer returns `markedElements`.
- **One extension ID.** The bridge accepts only this project's extension ID. A build with its own key needs its ID added to `EXTENSION_IDS`.

### Added

- **Module switch.** Workato is now a module, with a switch in the extension popup (**Modules**). The switch is one per machine, kept in the bridge in `~/.mokutab/config.json` (`{"modules": {"workato": true}}`), so every Chrome profile shows and changes the same value. The first 2.x start records an explicit value: off on a fresh install, on after an upgrade from 1.x, where an upgrade is a machine on which `~/.workatomcp` or the 1.x bridge state dir (`%LOCALAPPDATA%\mcp-chrome-bridge` on Windows) exists. An explicit value, the person's or an earlier start's, is never rewritten; with `MOKUTAB_DATA_DIR` set nothing is recorded, and a module the file does not mention is off. While Workato is off, `tools/list` serves the 52 core tools, the server instructions say the module is off, and a Workato call is refused by the bridge and by the extension with the module name and where to turn it on (never "Tool not found"). A change sends `notifications/tools/list_changed` to every open MCP session (the stdio proxy forwards it within 2 s); a client that ignores it picks the change up in its next session. The Workato content script (the optional-fields outline) does nothing while the module is off. With no bridge connected the popup switch is disabled. A malformed config file keeps the last good state and is reported in the bridge log. When a bridge connects, the extension forgets the state it stored until that bridge pushes its own, so a bridge older than the switch is never stuck with a stale "off".
- **Data dir move.** A bridge start renames `~/.workatomcp` to `~/.mokutab` when only the old one exists, before anything reads the data: one rename on one volume, so the function registry and `config.json` move whole or not at all. It never copies, never deletes and never fails the start. When the rename fails (an open handle on Windows: `EPERM` or `EBUSY`), that run keeps using `~/.workatomcp`, logs it to stderr and records it in the bridge state dir for `doctor`; the next start tries again. Until the move has happened, every process (`doctor` and the stdio proxy too) reads `~/.workatomcp`, so none sees half of the data. With both present, `~/.mokutab` wins. An override (`MOKUTAB_DATA_DIR`) is used as is and never moved.
- **Doctor checks for what 1.x leaves behind**, read-only, each with the command to run:
  - the old package still installed globally (`npm uninstall -g workatomcp-bridge`);
  - a native host manifest whose target is gone, or points into the old package (`mokutab-bridge register`);
  - a Claude Code registration (`~/.claude.json`, or `CLAUDE_CONFIG_DIR`) that reaches this bridge under the key `workato`, at user or project scope, with the `claude mcp add` and `claude mcp remove` commands for that scope. Only keys and scopes are reported, never the entries, and a `workato` server that is not this bridge is left alone;
  - the data dir: not moved yet, a move that failed (with the error, and how to free the handle or move it by hand with Chrome closed), or both dirs present (how to copy a function across and commit it by hand, since an uncommitted copy of a vault function does not run).
- Commands `mokutab-bridge` and `mokutab-stdio`. `workatomcp-bridge`, `workatomcp-stdio`, `mcp-chrome-bridge`, `chrome-mcp-bridge` and `mcp-chrome-stdio` stay as aliases of them until 3.0.
- `@mokuhub/mokutab-shared` exports `WORKATO_TOOL_ALIASES`, `aliasDescription` and `aliasOffMessage`.

### Changed

- **The name.** The MCP handshake says `MokuTab`, and so do the extension name, its action title, the popup and the page titles; the popup footer reads "browser tools for ai agents". The popup's MCP config copy and the welcome page register under the key `mokutab`, and the welcome page starts with the core tools and presents Workato as a module. The release zip is `mokutab-extension-X.zip`. The repository moves to `MokuTeam/MokuTab` (GitHub redirects the old URL). The native host id `com.chromemcp.nativehost`, the extension ID and the plugin marketplace id (`workato-mcp`, which installed plugins are keyed by) stay. `LICENSE` names MokuHub LLC as the copyright holder.
- **Environment variables.** Every bridge override that was `WORKATOMCP_*` is now `MOKUTAB_*`: `MOKUTAB_DATA_DIR`, `MOKUTAB_FN_DIR`, `MOKUTAB_FN_STATE_DIR`, `MOKUTAB_BW_PATH`, `MOKUTAB_STRICT_TABS`, `MOKUTAB_UPDATE_STATE_DIR`, `MOKUTAB_OPERATIONS_DIR`. The `WORKATOMCP_*` name each one replaced is still read when the new one is unset or blank, until 3.0.
- **Temp and log dirs.** Spilled results go to `<tmpdir>/mokutab-results`, the operations journal's fallback to `<tmpdir>/mokutab-operations`. The wrapper logs go to `%LOCALAPPDATA%\mokutab-bridge\logs` on Windows, `~/Library/Logs/mokutab-bridge` on macOS and `$XDG_STATE_HOME/mokutab-bridge/logs` (or `~/.local/state/mokutab-bridge/logs`) on Linux. The bridge state dir keeps its 1.x name (`%LOCALAPPDATA%\mcp-chrome-bridge`, `~/Library/Logs/mcp-chrome-bridge`, `$XDG_STATE_HOME/mcp-chrome-bridge`), so the update flag, the default profile, watches, the function run log and the operations journal stay where they are.
- **Function registry identity.** `chrome_fn_save` commits as `mokutab <mokutab@localhost>`. The vault gate lets a function read the vault only when a person made its last commit, and both `mokutab` and the 1.x `workatomcp` identity count as the machine, permanently, by name or by email, as author or committer: a function 1.x saved does not suddenly look hand-committed. The page-side markers follow the name, `__mokutab_fn` (the function runner's result) and `__mokutabJobs` (the async job store of `chrome_javascript`); a job started in a page before the extension reload is lost, as it already was.
- **Internal layout: core and modules.** Workato code moved behind a module interface on each side: `packages/shared/src/modules/workato` (names, schemas, instructions snippet), `app/native-server/src/modules/workato` (file IO, the recipe engine and mutators, callable schema, save with dependents, the operations journal, step schema, LCAP IO, datapill, py_eval lint, switch environment, recipe callers, and the workspace pin), `app/chrome-extension/entrypoints/background/modules/workato` (the executors, the context-block hook, the content-script gate). Core never imports a module, which a test on each side checks. `@mokuhub/mokutab-shared` adds `CORE_TOOL_NAMES`, `CORE_TOOL_SCHEMAS`, `MODULES` and the module message types; `TOOL_NAMES` and `TOOL_SCHEMAS` keep the whole catalogue (core first in `TOOL_SCHEMAS` now). Apart from the four new names, every schema is byte for byte what 1.13.0 served. The core bridge files lose the `workato` prefix (`auto-file.ts`, `bridge-info.ts`, `reload-extension.ts`).
- `chrome_bridge_info` counts and hashes the catalogue that is actually served: 52 tools with Workato off, 153 with it on (52 core, 97 Workato and the four aliases). Its `schema_revision` therefore differs from 1.13.0's. It no longer triggers the Workato workspace re-check after a profile reconnects (it never sends anything to the extension), and it does not take `out_file`.
- The function registry (`~/.mokutab/functions`) and the config file come from one data-dir helper, which the registry asks on every use, so a bridge that started before another process moved the data dir follows the move. `MOKUTAB_DATA_DIR` overrides the directory (the test setup uses it).
- On an extension update, the background removes the data only the removed features wrote: the `rr_*` storage keys, `agentTheme`, `userscripts` and `userscripts_disabled`, and the IndexedDB databases `rr_storage`, `rr_v3` and `element_marker_storage`.
- A bridge older than 2.0 still asks the extension for the record-replay flow list on every `tools/list`. The extension now answers at once with an empty list instead of leaving it to wait 20 s. This compatibility shim goes away in a later release.
- The bridge declares `zod` itself: the MCP SDK it loads lists it as a peer, and no other package declares it any more.

### Removed

- **Record-replay**: the recorder, both replay engines, saved flows, and the `flow.*` tools the bridge listed for published flows (there were none). Saved browser functions (`chrome_fn_*`) cover the same ground.
- **Unlisted tools** that the bridge forwarded by name but never listed: `chrome_userscript` and the options page that managed userscripts, `chrome_inject_script`, `chrome_send_command_to_inject_script`, `chrome_get_interactive_elements`, and direct calls to the network capture sub-tools (`chrome_network_capture` still drives them).
- **The element marker**: the "mark element" context menu, its overlay and its IndexedDB store. `chrome_read_page` no longer returns `markedElements`, which nothing could fill any more.
- The agent chat themes. The popup and the welcome page keep the default look.
- The bridge's `/ask-extension` echo route.
- **Shared package exports**: `rr-graph`, `step-types`, `labels`, `node-spec`, `node-spec-registry`, `node-specs-builtin` and `agent-types` are no longer exported, nor are `NativeMessageType.PROCESS_DATA` and `PROCESS_DATA_RESPONSE`. Record-replay, the agent chat and the echo route were their only users. This changes the package's public API.
- Dead code and dependencies: an empty content script, 132 unused UI strings, the unused `csrf.ts` helper and the four `*.stub.ts` planning files (their notes stay in `docs/design/plans/`), the flow builder and Quick Panel styles, `chalk`, `pino`, `zod` in the shared and extension packages, and the icon plugins, among others.
- Manifest permissions `contextMenus`, `alarms` and `declarativeNetRequest`, which only the removed code used, and `'wasm-unsafe-eval'` in the extension CSP with the cross-origin isolation headers (`cross_origin_embedder_policy`, `cross_origin_opener_policy`): nothing uses WebAssembly or SharedArrayBuffer since the semantic engine went in v1.3.

### Fixed

- **The bridge's origin check was a prefix match.** The extension WebSocket (`/ws-client`) and CORS on the HTTP routes accepted any origin starting with `http://127.0.0.1` (so `http://127.0.0.1.attacker.tld` too) and any `chrome-extension://` or `moz-extension://` origin. A page or another extension that got through could register under an existing profile name, replace the live socket and receive that profile's tool calls. Origins are now parsed and compared exactly. The WebSocket takes no Origin or this extension's id only, and refuses anything else with a 403 at the upgrade, logged to the bridge's stderr (it used to accept the socket and close it, so a refused client saw a working bridge and reconnected about twice a second, silently). CORS takes the same, plus `http://127.0.0.1` on any port for local debugging pages. `EXTENSION_IDS`, which the native-messaging manifest (`register`) also uses, holds only this project's id now; upstream's Web Store id `hbdgbgagpkpjffpklnamcljpakneikee` is gone. A build with its own extension key needs its id added there.
- **The HTTP routes ran for any caller.** CORS only withholds response headers, so `/file` (which reads a local file by path) and `/mcp` executed for a simple cross-origin request from any page, and a DNS-rebinding page is same-origin with the bridge. Every route now refuses, with a 403 before it runs and a line on stderr, a request whose Origin is present and not allowed, or whose Host is not `127.0.0.1:<port>` or `localhost:<port>` (the port the request came in on). MCP clients send no Origin and that Host, and keep working. `/file` takes the WebSocket's rule, no Origin or this extension only: no local page needs it.
- `chrome_read_page` falls back to the interactive-elements helper when the accessibility tree is too sparse, but the fallback never reached it: the accessibility helper answered the ping meant for the second helper, so it was not injected and the fallback failed. It now injects the helper and returns the elements.
- `doctor` and `report` did not find the wrapper logs: they looked in a `workatomcp-bridge` log dir while the wrappers wrote to `mcp-chrome-bridge`. All three now use `mokutab-bridge` (see Changed).

### Migration

WorkatoMCP 1.x is now MokuTab. Same extension ID, same native host, new package, new data dir and a new registration key. Upgrade in this order:

1. **Quit Chrome completely**, every profile. The running native host locks the old package's files on Windows.
2. **Remove the old package:** `npm uninstall -g workatomcp-bridge`. It must come before the install: the new package keeps the old command names (`workatomcp-bridge`, `workatomcp-stdio`, `mcp-chrome-bridge`, `chrome-mcp-bridge`, `mcp-chrome-stdio`) as aliases until 3.0, so installing over the old package fails with `EEXIST`. `--force` is not a workaround: a later uninstall of the old package deletes the shared command names.
3. **Install the new one:** `npm i -g @mokuhub/mokutab-bridge`. Postinstall registers the native host under the same id.
4. **Put the 2.0.0 extension in place:** unzip the release zip over the folder Chrome loads the extension from, or rebuild the repo (`app/chrome-extension/dist/chrome-mv3`). It has the same extension ID, so it replaces the old one in place and keeps its permissions, including the userScripts toggle.
5. **Start Chrome.** The first bridge start moves `~/.workatomcp` to `~/.mokutab`. If something holds that directory open, the move is retried at the next start; `mokutab-bridge doctor` says whether it happened.
6. **Re-register in Claude Code:** `claude mcp add --transport http -s user mokutab http://127.0.0.1:12306/mcp`, then `claude mcp remove workato -s user`, then restart the sessions. The old names of the four renamed tools (`workato_list_profiles`, `workato_switch_profile`, `workato_bridge_info`, `workato_reload_extension`) keep working until 3.0 while Workato is on. Permission allowlists that name `mcp__workato__*` need the new prefix `mcp__mokutab__*`.
7. **Check:** `mokutab-bridge doctor`. It flags what 1.x left behind: the old package, a native host manifest pointing into it, a Claude Code registration still under `workato` (user or project scope, with the command that removes it), and a data dir that has not moved.

Workato stays on after an upgrade: a machine where `~/.workatomcp` or the 1.x bridge state dir exists counts as one. Switch it off in the popup if you do not need it.

## bridge 1.13.0 · shared 1.11.0 (2026-10-19)

Browser flows saved once and run by name, logins without a subagent, and a py_eval check that agrees with Python.

### Added

- **Browser functions**: `chrome_fn_list`, `chrome_fn_get`, `chrome_fn_run`, `chrome_fn_save`, `chrome_fn_runs`. A function is a named, versioned sequence of steps (`navigate`, `wait_for`, `js`, `verify`, `tool`, `pause`, `finish`, `fail`) with JSON Schema params, kept as one YAML file in a private git registry (`~/.workatomcp/functions`, every save a commit). A run opens a window of its own and closes it at the end. A `write` or `send` without `confirm` returns a preview and a `run_id`, and the confirmed call commits exactly that in the same window; a failure at or after a commit is reported as `unknown` with a hint on how to check, never retried. Saves are refused on top of a newer version. Optional dedupe keys, host checks before commits, and a run log that records param hashes, not values. See [TOOLS.md](docs/TOOLS.md#browser-functions).
- **Logins from the vault**: a function can type values from the user's Bitwarden vault (`vault` in the definition, `"{vault.password}"` as a fill value). The bridge reads them with the `bw` CLI at the step that types them, only on pages that match the vault item's URIs, and scrubs them from everything it returns; no model sees them. Such functions are written and committed by a person: `chrome_fn_save` refuses them and a run requires the committed file. The first one, `netsuite.login`, replaces the login subagent.
- Extension messages `agent_tab_info` and `agent_tab_navigate`: a tab's URL and load state, and navigation that waits for the new page, through the tabs API only. Closing an agent tab reports whether it is really gone.

### Fixed

- The py_eval check refused valid Python and blocked recipe saves: a block opened by a multi-line `if (...):` condition (or a backslash continuation) read as "unexpected indent", and any tab in a file that also used spaces read as a TabError. The indentation check now follows CPython's tokenizer (both tab widths, statement ends across brackets and backslashes), and when a real Python compiles the code, the structural lint's findings become notes instead of blocking the save.
- `workato_test_recipe` refused recipes using JSON tools, Message templates or Lookup tables ("needs a connection"): those adapters, and Utilities, Webhooks, Data tables, XML tools, Lists and FileStorage, need none (`connection_required: false` in Workato's own meta). It now also refuses to test a RUNNING recipe, before anything is sent: a test ends with the recipe stopped, which would have left it, and its callers, broken.
- `workato_recipe_save_with_dependents` stopped the callers before the save's own checks ran (code_path, py_eval), so a refused save left them stopped until the restore. Those checks now run first; a refused tree stops nothing.
- Output redaction no longer hides ordinary fields whose names merely contain a short marker: `subsidiary` (holds `sid`) and `author` (holds `auth`) came back as `<redacted>`. `sid` and `auth` now match a word of the key; longer markers still match anywhere, so `cookies`, `credentials` or `passwordhash` stay redacted. The sanitizer moved to `workatomcp-shared` so the bridge redacts with the same rules.

## bridge 1.12.0 · shared 1.10.0 (2026-10-13)

Files that reach the disk intact, page scripts that outlive the call, and redaction that no longer swallows templates.

### Added

- **Extension releases**: pushing a `vX.Y.Z` tag (the extension version) publishes a GitHub release with `workatomcp-extension-X.Y.Z.zip`, built by GitHub Actions from that tag and attested (`gh attestation verify`). Installing the extension no longer needs a clone and a pnpm build.
- **`chrome_fetch_to_file`**: fetches a URL in the tab's page with the session cookies and writes the body straight to a local file (up to 40 MB). The bytes never enter the reply or the output redaction, so PDFs from print URLs, CSV exports and template sources arrive intact. The reply is a summary: path, size, sha256, status, content type, filename and the first bytes (`%PDF-1.4`). It replaces Blob plus `anchor.click()` downloads.
- **Async jobs in `chrome_javascript`**: `async_job:true` starts the code and returns a `job_id` at once; `job_id` with `wait_ms` polls it. A page whose main thread is blocked (a sync XHR) reports `busy` instead of timing the call out, and a job whose page navigated away reports `lost`.
- **`chrome_upload_file` by `uid`**: a file input from `chrome_snapshot` is reached by its uid, including inputs inside same-process iframes.

### Changed

- `chrome_javascript` with an explicit `out_file` writes the returned value itself to the file, unredacted, and returns its size and sha256. Inline results and automatic spills are still redacted.
- A full-page or element screenshot of a hidden tab in the shared agents window moves that tab into its own unfocused window first and reports `moved_to_window`. Leasing with `own_window` up front is no longer needed for screenshots. Tabs outside the agents window are never moved.
- `chrome_handle_download` says why it timed out: no download started (and that Chrome's "multiple automatic downloads" permission holds script-started ones silently), or which download started and how far it got. An interrupted download fails at once with its reason.

### Fixed

- The output redaction replaced any text with two `&`- or `;`-separated pieces containing `=` with `[BLOCKED: Cookie/query string data]`, which swallowed whole HTML templates and full URLs. Only a string that is itself a cookie, Set-Cookie or query string is blocked now, and URL paths are no longer taken for base64.
- `chrome_navigate` to a slow page (a PDF still being generated) reported the previous page with `navigated:false`, which read as "nothing happened". The reply now carries `pending_url` and a note not to navigate again.

## bridge 1.11.0 · shared 1.9.0 (2026-10-05)

Agents that sleep until a page changes instead of polling it.

### Added

- **Background watches**: `chrome_watch_start` runs an agent-written script in chosen tabs (by tab id or url pattern, any profile) every N seconds and records an event when the result changes: an array wakes only on items not seen before, any other value when it differs. The agent sleeps on `watch-wait` (a CLI that long-polls the bridge and exits with the events), so a quiet page costs no tokens. One wait can cover several watches. Watches survive bridge restarts and expire after `ttl_minutes`. Also `chrome_watch_list`, `chrome_watch_stop`, `chrome_watch_events`.
- Readings run through `chrome.userScripts` when "Allow User Scripts" is on for the extension (no debugging banner, page CSP does not apply), otherwise through the debugger.

## bridge 1.10.0 · shared 1.8.0 (2026-09-30)

Agents that know what their actions did. Ideas taken from chrome-devtools-mcp and browser-use.

### Added

- **Wait and report after every action**: clicks, fills, keys, `chrome_computer` and `chrome_navigate` wait for any navigation they started and for the DOM to go quiet, then report the final url and title, whether it navigated, an open JS dialog and tabs the action opened (`settle`, `settleTimeoutMs`). `chrome_navigate` now reports the page it landed on.
- **JS dialogs**: a dialog an action opens is reported at once ("the action ran and opened a confirm dialog ... answer it with chrome_handle_dialog") instead of hanging; input tools and `chrome_snapshot` refuse or report while one is open; `chrome_handle_dialog` answers it even though the page is blocked.
- **Snapshot**: uids stay the same while an element exists (a gone element or a navigated page is refused, never guessed); element state (value, checked, expanded, selected, disabled, required, url, select options); same-process iframes; clickable elements found by cursor; no 50k truncation (large results spill to a file).
- **Real clicks and smart fills**: `chrome_snapshot_click` scrolls into view, refuses a covered element naming what covers it, returns a select's options, and reports checkbox state; `chrome_snapshot_fill` handles select, combobox, checkbox, radio and switch and reads the value back. In a hidden leased tab both fall back to DOM events and direct value setting.
- New `chrome_snapshot_fill_form`, `chrome_act` (several uid actions in one call), `chrome_search_page`, `chrome_find_elements`; `chrome_javascript` takes `uids`; `chrome_get_web_content` reads in chunks (`startChar`, `maxChars`); `chrome_lease_tab adopt_tab_id` leases a tab an action opened.

### Fixed

- `chrome_navigate` with a tab failed on URLs Chrome cannot turn into a match pattern (an IP with a port).
- A call waiting behind a dialog-blocked call on the same tab could deadlock `chrome_handle_dialog`.

## bridge 1.9.0 · shared 1.7.0 (2026-09-29)

Parallel agents on one MCP server, in the same or different Chrome profiles.

### Added

- **`chrome_lease_tab` / `chrome_release_tab`**: each agent leases its own tab (in an unfocused agents window, or its own window with `own_window`) and passes `lease` on every call; the bridge turns it into the right profile and tabId and never activates the tab. While a session holds leases, a tab-targeting call without `lease` or tabId is refused (`WORKATOMCP_STRICT_TABS=1` makes that permanent). Idle leases expire after 30 minutes.
- `tabId` on `chrome_network_request`, `chrome_handle_dialog`, `performance_*` and `chrome_network_capture`.

### Fixed

## bridge 1.6.0 · shared 1.3.0 (2026-09-07)

Recipe development efficiency: one guarded mutation engine, bounded reads, job and caller search that does not make an agent walk pages, recoverable multi-recipe saves, supported test execution, and a session that cannot silently change workspace. Implements [`docs/design/plans/2026-09-07-recipe-development-efficiency.md`](docs/design/plans/2026-09-07-recipe-development-efficiency.md); the endpoint captures behind it are in [`skills/workato-recipes/platform-endpoints.md`](skills/workato-recipes/platform-endpoints.md).

**Upgrade note: the bridge and the extension must be updated together.** The three legacy recipe mutators (`workato_recipe_add_step`, `workato_recipe_set_step_input`, `workato_recipe_map_datapill`) moved out of the extension and into the bridge, and `app/chrome-extension/entrypoints/background/tools/workato-recipe/` is deleted. An old bridge against a new extension would forward those names to an extension that no longer has them. A new bridge against an old extension is fine. Rebuild `packages/shared`, rebuild and reload the unpacked extension, and restart the MCP client: the server name, version, instructions and tool catalogue all changed at initialize.

### Recipe editing engine and batch apply

- **A shared mutation engine** (`workato-recipe-engine.ts`) behind every native recipe write: the surgical mutators, the batch tool, the three legacy names and the callable-schema tools now pull once with `view: "full"`, mutate a deep clone, renumber the whole tree when structure changed, derive schemas, validate locally, MERGE the pulled config, save once and summarize once. A stale caller-supplied `expected_base_version_no` is refused after the pull and before any operation runs, so operations are never computed against a tree the caller never saw.
- **`workato_recipe_apply`**: several recipe edits in ONE pull, validate, save, readback cycle, so five mappings create one version instead of five. Up to 50 ops: `set_input`, `delete_input`, `set_extended_schema`, `set_py_eval_code`, `map_datapill`, `derive_schema`, plus the structural ones the surgical tools never had, `insert_step`, `remove_step`, `move_step`, `set_loop_source`, `bind_connection`. Steps are addressed by number, `as` anchor, or uuid, and a number that appears twice in a tree an older renumbering bug corrupted is refused rather than resolved to the first hit. Every change is applied to a CLONE: one invalid operation refuses the whole batch before anything is written, naming the change index, the step and the reason. `dry_run` returns the same summary (validation, `changed_paths`, `would_save_version`) without saving; `idempotency_key` makes a retried batch return the stored summary instead of creating a second version. `remove_step` refuses while a datapill still references the node, and `force: true` names what it found; it also drops the `config` entry of a provider no remaining step uses, but only when that entry carries no `account_id`, because dropping a live binding is not a decision a step deletion should make.
- **Local validation covers what Workato accepts silently and then runs wrong**: globally sequential numbering including nested blocks, unique 8-hex `as` anchors, a `uuid` on every node the call creates (the live probe: a node without one is rejected with `code is invalid: line=0, uuid not present`), `else`/`elsif` last inside an `if` block, `catch` last inside `try`, `while_condition` first inside `repeat`, and a `foreach` whose `source` sits at the node root rather than under `input`. Those rules are errors on nodes the call created or changed and warnings on untouched nodes, so a recipe with a pre-existing quirk stays editable.
- **Mutation responses distinguish persisted, valid and verified**, alongside `changed_paths` and `version_no`. A save that stored a tree Workato rejects is persisted and NOT valid, and used to read exactly like a clean edit. `workato_ui_save_recipe_code` carries the same triple, plus `save_status: "persisted_invalid"` when `code_errors` is non-empty (`isError` stays false), `restart_skipped_invalid`, and `py_eval_warnings`.
- **`workato_recipe_validate`**: check a recipe locally, before a save creates a version. Workato has no validate-without-save endpoint (`validate.json` and `ready.json` are both 404), so the only way to learn a tree was wrong has been to save it and read `code_errors`. The tool runs the checks that need nobody's permission: structure, connection bindings (every connection-backed provider has a config entry carrying an `account_id`, the exact gap Workato reports only later and only in `state.json` as `account_id can't be blank`), datapill references (every `_dp` pill and every Variables `<uuid>:<as>` composite points at a step that exists and runs earlier, each break reported with the step and the exact path), and the two silent-strip rules on extended schemas. It takes `recipe_id` (pulls the saved recipe), `code_path` (a pulled file) or `code` (a tree you are about to save), and it never calls the save tool. Finding codes: `structure`, `config_absent`, `config_unparseable`, `config_entry_missing`, `account_id_missing`, `config_entry_unused`, `broken_datapill`, `broken_variable_reference`, `datapill_not_upstream`, `declaration_missing`, `missing_extended_schema`, `structured_input_no_schema`, `datapill_target_no_output_schema`.
- **Validation says what it does not cover**, in the response and in the tool description: `coverage` reports `formulas: false` and `runtime: false`, because formulas are Ruby and are not parsed and nothing is executed. A `valid: true` result means the local checks passed, not that the recipe runs.
- **Validation follows Workato rather than the authoring guidance where the two differ.** A non-hex `as` on an existing step is a WARNING, not an error: Workato does accept anchors such as `tjcall01`, and refusing them would strand a legacy recipe. A step inside a `catch` reading its own `catch.<as>.message` is not a forward reference, because the catch node is in scope for its own block. And a `catch` never needs an `extended_output_schema`, so `datapill_target_no_output_schema` does not fire on one.
- **Extended schemas are derived from the recipe's own declarations.** Workato drops a structured input whose `extended_input_schema` is missing, reports `code_errors: []`, and shows the loss only on readback; the same silence applies to an output a datapill reads. Those schemas are mechanical restatements of a declaration the step already carries, so `workato-recipe-schema.ts` derives them: `declare_list` and `insert_to_list` from `list_item_schema_json`, `declare_variable` and `update_variables` from `variables.schema` (the two composite forms resolve their declaring step through the `<uuid>:<as>[:<variable>]` lookup key), and the clock trigger's `trigger_every` from its own time unit. The declaration is the only source: a list holding three strings today says nothing about the type its author declared, so a missing declaration is refused with a reason rather than guessed from the current values. Evidence is reported per derivation, `verified` for `declare_list` and the clock trigger, `documented` for the other three.
- **`auto_schema`, on by default**, advertised on `workato_recipe_apply`, `workato_recipe_add_step` and `workato_recipe_set_step_input`, and applied by the engine to every other native mutator. Before each save it fills in the schemas the tree's declarations imply, corrects one that has drifted, and reports each as `derived_schemas: [{step, step_number, kind, fields, schemas, status, evidence, differences?}]` with `changed_paths` naming the schemas it wrote. The whole tree is covered, not only the edited steps, because a save rewrites the whole tree: an untouched `declare_list` with no schema loses its items on this save too. Agreement is compared structurally, never on `label` or `control_type`, so a save does not churn a schema that already works, and derived nodes are not marked as edited, so filling in a schema cannot promote an unrelated quirk into a refusal. `auto_schema: false` turns it off, and a `derive_schema` op does one step explicitly, replacing even an agreeing schema. `call_recipe`'s `input.parameters` is deliberately excluded: `workato_caller_bind` owns that key.
- **A clock trigger keeps its schedule.** Saving `{time_unit, trigger_every}` alone came back without `trigger_every`: the save reported `code_errors: []` and the readback showed the field gone (probed live, minutes and days alike, which contradicts what `code-tree.md` said). The derived schema declares it as the select Workato expects, with the value the step already carries always inside the option list.
- **The legacy mutators no longer unbind every connection in the recipe.** `workato_recipe_add_step`, `workato_recipe_set_step_input` and `workato_recipe_map_datapill` rebuilt the `config` array from the providers found in the code tree, which dropped `account_id` from every entry and reset `skip_validation`. Reproduced live in the audit: one added step silently unbound both Salesforce and NetSuite. All three now run through the engine, which MERGES the pulled config and only appends entries for a provider the recipe did not already use. A new provider gets its `account_id` when `connection_id` is given, and otherwise the response says `connection_binding: missing` rather than leaving a recipe that cannot start.
- **`workato_recipe_add_step` renumbers the whole tree and can insert into a nested block.** It renumbered only the top-level block, so an insert at position 0 gave a nested step and a top-level step the same number, and any `after_step` inside a `foreach`/`if`/`try` returned "not found". Insertion now takes an `anchor` (`after` / `before` / `into` with `first` / `last`), keeps `elsif`/`else`/`catch` at the tail of their parent block and a `while_condition` first, and repairs numbering left broken by an earlier save. Its `keyword` enum matches the code tree: `action`, `if`, `foreach`, `repeat`, `try`, `stop`. `repeat_each` and `return_result` were never keywords (a foreach is `foreach`, a return_result is an `action` named `return_result` on `workato_recipe_function`) and produced a malformed node with no `block`, `source` or `condition`. Only `recipe_id` is required now; `provider` and `action_name` are required at runtime for `keyword: "action"`.
- The three legacy mutators, plus `workato_recipe_delete_input_path`, `set_py_eval_code` and `set_extended_schema`, advertise the save modifiers their handler already forwarded: `expected_base_version_no`, `comment`, `verify_readback`, `restart_if_running`, `ensure_running`, and `dry_run` where it applies. `set_step_input`'s `step_number` also accepts a uuid, and `map_datapill`'s `path` supports the `name#size` accessor.
- **The optimistic lock fails closed.** `workato_ui_save_recipe_code` skipped the version check whenever the status probe failed, which is exactly the case where a stale tree can overwrite a newer one; when `expected_base_version_no` was requested and the current version cannot be read, the save is refused.
- **A save that Workato reports validation errors on no longer restarts the recipe.** The payload carries `save_status: "persisted_invalid"`, the automatic restart is skipped (`restart_skipped_invalid: true`, `running_after_save: false`), and the first line says the recipe is stopped rather than reading as a clean save.
- **py_eval shadowing warnings from a whole-tree file save reach the response.** `workato-file-io.ts` computed them into `args.py_eval_warnings` and nothing ever read them; the save payload now carries `py_eval_warnings`.
- **A version diff no longer invents added and removed steps.** Nodes without an `as` were keyed by walk order, so inserting one anonymous node near the top shifted every later one's counter: the diff named an untouched node as added and attributed the new node's content to the node that used to hold its number. Anonymous nodes are now keyed by their `uuid`, which survives an insertion above; every step header carries `uuid`, and the counter remains only for a node that has neither.

### Bounded reads, projection and grep

- **Projection parameters on `workato_pull_recipe`, independent of each other.** `include` picks the sections of a step view (`mappings`, `fields`, `datapills`, `schemas`, `code`; default `["mappings","fields"]`, so upstream pills are opt-in), `paths` returns exact values losslessly, `fields` filters by field name or label, `steps` reads several step refs against ONE snapshot, and `if_version` answers `{unchanged: true, version_no}` without transferring the recipe again. Every view now carries `version_no`, including a step view, which had none.
- **Every list has a limit, a total and a cursor.** `max_items` (default 60, hard maximum 500) and `budget_chars` (default 12000 for a step view, 60000 for compact and outline) apply to every list in the response, including the compact step tree. A list cut by either is cut at an item boundary, says `truncated: true`, and carries a `next_cursor` that continues without repeats. Exact `paths` reads are exempt: a lossless read stays lossless.
- **`field_query` is now `fields`, and a filter no longer removes the limit.** The old parameter lifted the 60-item cap on `fields` and `available_datapills` while returning every mapping uncapped, so the broad search that most needed a bound was the one without one. A filter now narrows the lists inside `max_items` and the budget. `field_query` remains as an alias with the same behaviour, and its schema text no longer claims that a field is matched by `ref` (fields match name and label; a datapill matches ref and label).
- **Compact and outline keep what the recipe actually does.** The allowlist copied `input` and dropped every other node-root key, which silently lost `source`, `repeat_mode`, `clear_scope`, `batch_size` and `comment`: a compact view of a loop did not say what the loop iterated. All of them are kept now, the loop source appears in the step header too, and if/else/try/catch structure is unchanged. Outline gains `input_keys`, the top-level input keys of each step, in place of the input it drops.
- **Long embedded values are previewed, not copied whole.** A compact recipe reached 94k characters because `list_item_schema_json`, `output_schema`, `code_output_schema_json`, sample documents and Python or SQL bodies were copied verbatim. Anything over 240 characters is now replaced by a marker that names the way back, `<<preview 240 of 9021 chars; path=input.code; read with step:"py01", paths:["input.code"]>>`, followed by the first 240 characters. `paths:[...]`, `include:["code"]` and `view:"full"` all return the value verbatim.
- **`workato_recipe_grep`**: find a string inside one recipe without pulling the recipe into context. The tree is already in the service worker after one fetch, so the search runs there and only the MATCHES come back, each with the step it belongs to (`number`, `as`, `keyword`, `provider`, `name`, `title`), the exact path, a bounded snippet and the full length of the value. The path it reports is the one `workato_pull_recipe(step, paths:[...])` reads back losslessly, so a hit turns straight into an exact read. `match` is `substring` (default, case-insensitive), `word` or `regex`; a regex is limited to 200 characters, refused when a quantifier is applied to a group that already contains one (the `(a+)+` shape behind every real hang), and run against the first 20000 characters of each value, because a service worker has no RegExp timeout. `scope: "all"` covers input, conditions, titles, descriptions, comments, the foreach source, the extended schemas, the picker selection that holds a called recipe's NAME (the id alone is in `input.flow_id`) and the job report columns on the trigger; `scope: "input"` searches the configured input only. `total_matches` counts matching values, one per value, so it means "places", not "hits".
- **A version-pinned snapshot cache in the service worker.** Metadata is fetched first and the code is then requested for that exact version (`code.json?mode=view&version_no=<n>`), so the two halves of the answer describe the same snapshot. A second read of the same version skips the code fetch and reports `cache_hit: true`. The cache is bounded (32 entries, 20 MB) and keyed by tab host, recipe and version, so a stale entry cannot be served: its key simply stops matching. `workato_list_jobs`, `workato_test_recipe` and `workato_recipe_callers` read through it as well, instead of issuing their own metadata and code pairs.
- **Every extension write path drops the recipe's cached snapshot.** `workato_ui_save_recipe_code`, the editor's Save button (`workato_ui_save_recipe`, which resolves the recipe id from the tab URL), rename, delete and copy all call `invalidateRecipeSnapshot`. A version-keyed entry could never have been served stale, but the memory was held until the LRU reached it, and a write path that does not invalidate is one refactor away from being wrong.
- **A step with no schema of its own now says what it accepts.** `workato_pull_recipe(step)` returned `fields: []` whenever the step's `extended_input_schema` was empty or absent, which reads as "this step takes nothing" rather than "the field list lives on the adapter". A step view that asks for fields now merges in the adapter's own input fields for that exact operation, read once per call from `/integrations/meta` and only for the steps that need it. Each field carries `provenance` (`static`, `dynamic` or `both`) and the view carries `fields_complete`: false when nothing could be read for the operation, and false when the adapter derives its input per connection or object, because a floor is not a whole set. Connectionless built-ins are covered like any other adapter.
- **A `foreach` no longer disappears from the datapills a step may reference.** `collectUpstreamDatapills` required a `provider`, and a loop node has none, so the current loop item, the pill most often needed inside the loop, was never offered. Loop nodes now contribute `foreach.<as>`. Visibility is also structural (document order) rather than numeric when the target step is known: ancestors and their earlier siblings are upstream, later siblings and other branches are not.
- `out_file` on `workato_pull_recipe` drops the new projection parameters along with `step` and `field_query`. The file gets the whole lossless tree, so a projection would either be ignored or cut what is written, and a partial recipe must not reach disk under a name that reads as complete.

### Jobs and search

- **`workato_list_jobs` searches jobs instead of making the agent walk pages.** `query` is Workato's own search and, measured against a retained job, it matches a contiguous case-insensitive substring of the job id or of a custom job-report column value only: not the error text, not the column labels, and never an erased job. The new `match` `{mode: exact|substring|regex, fields, value}` is a LOCAL scan applied to every job the walk sees, inside the page, so a 5000-job scan crosses the page boundary as a handful of matches. The two budgets are separate: `limit` caps matches RETURNED, `scan_budget` caps jobs SCANNED (default 500, max 5000). The local regex is always case-insensitive; there is no flags argument.
- **Every `workato_list_jobs` response says how much was actually looked at.** `coverage` carries search_mode, scanned, matched, erased_seen, the started_at window, complete, retention_boundary_reached, stopped_reason and a `next_cursor` taken from the last SCANNED job, so a scan that matched nothing is still resumable. The `summary` sentence refuses to call an incomplete scan an absence: zero matches with a filled budget says so, in words, next to the cursor that continues it.
- **A custom job date range.** `started_from` / `started_to` accept ISO-8601 with an offset, a bare `YYYY-MM-DD` (widened to 00:00:00 and 23:59:59) or a local `YYYY-MM-DDTHH:MM(:SS)` resolved in `timezone` (default UTC, an offset or an IANA name), and are sent as the `started_at_from` / `started_at_to` parameters the recipe Jobs page uses. That makes a November to December interval expressible. `started_at` also gained the `1.hour` and `24.hours` presets, and now REJECTS any other value: Workato ignores an unknown window silently and answers with the unfiltered scope, which reads as "no such jobs".
- **`workato_list_jobs` stops at the retention boundary.** Three consecutive erased jobs end the walk (`stop_on_erased: false` to continue), and the response says so. Verified across five recipes: the sweep is workspace-wide, not per recipe, so everything older than the boundary is erased too and scanning on spends pages for nothing. The boundary MOVES, so `coverage` describes the scan that produced it and never a workspace fact: on 2026-09-07 the first probe put it around Jul 16 to Jul 20, and by 19:45 UTC the same day a job from Aug 3 on recipe 72988590 was already erased.
- **An erased job no longer looks like an empty one.** A job swept by data retention stays in the list with `erased: true`, `report: null` and no `error` key even when it failed, and the slim shape coerced its title and columns to `''`, so unavailable data and empty data serialized identically and a failed job appeared to have no error. The slim job now carries `erased`, `zero_retention`, `is_test` and, for a called job, `calling_recipe_id` / `calling_job_id`, and reports title and report as `null` when erased.
- **An erased job's trace says the data is gone.** `/line_details` answers `[]` for a job swept by retention, and `workato_job_trace` projected that into a trace with zero steps: indistinguishable from a job that genuinely ran nothing. It now returns `{erased: true, zero_retention?, note, ...job header}` when the job metadata says the data was erased. `full: true` is unchanged, being a raw passthrough that carries `erased` on the job header already.
- **Report columns come back whole and labelled.** The slim job stopped at `custom_column_2` and renamed the columns to `col_0..col_2`, so columns 3 to 9 were dropped and nothing said what any of them meant. Every `custom_column_*` present is now returned, keyed by the label configured on the recipe trigger's `job_report_schema`, with `report_columns` listing the mapping, `report_columns_version` naming the version they came from, and unlabelled columns keeping their `custom_column_N` key. The labels are read from the version-pinned recipe snapshot rather than through an unpinned fetch behind a ten-minute cache, so a label changed inside that window is no longer served stale.
- **`fields` projection on `workato_list_jobs`**, for example `['id','started_at','status','report.Marker code']`. Unavailable data is reported as `null` with `erased: true`, never as an empty string, so a projected job cannot pass off "swept by retention" as "the field was blank".
- **Nested projection on `workato_job_trace`.** `paths` keeps only the requested paths inside each step's input and output (dots, `[N]`, `[]` for every element, `['a.b']` for a key with a dot), `max_items` previews long arrays as `{_array_preview, total, shown, items}` (default 20), and `fields` keeps only the requested keys per step. Projection runs before the summary is truncated, so the 500-character budget is spent on the data that was asked for, and the response echoes what it did under `projection`.
- **An explicit empty-value policy on `workato_job_trace`.** `empty: 'drop'` removes `undefined`, `null`, `''`, `{}` and `[]` and nothing else: `0` and `false` are diagnostic data and always survive, and arrays are mapped rather than filtered, so an element that prunes to `{}` keeps its index and every later index still means what it meant. Default stays `keep`. It is applied outside `stripSchemaNoise`, which re-stringifies embedded JSON, so a step's serialized input is never rewritten.
- **The `query` and `text` descriptions no longer promise searches Workato does not run.** `workato_list_jobs` claimed `query` was full-text over the job title AND error message; searching the error text of a retained failed job returns nothing. `workato_search_recipes` claimed `text` was a name substring match; it is a full-text search over name, description and the recipe's own action and trigger titles, which is why `ECO` answers with recipes whose steps say "New/updated records".
- **Explicit matching and filters on `workato_search_recipes`.** `match: name_substring | name_word | name_exact | name_regex` filters client-side over walked pages, `app` takes adapter technical names (one uses the server's `adapters=` filter, several are ANDed client-side), `running` filters client-side because Workato ignores the server parameter, and `max_pages` (default 5, max 50) bounds the walk while `coverage` reports pages_scanned, recipes_scanned, matched, complete and next_page. In the default full-text mode each hit carries `matched`, the highlighted name, description or action title with Workato's `<span class="text-highlight">` markup removed, so it is visible WHY a recipe came back. `sort` gains `relevance`.
- **A folder scope now means a folder.** `GET /web_api/mixed_assets.json` IGNORES `folder_id` outright: re-probed on 2026-09-07 with four variants (`folder_id`, `folder_ids[]`, `fid`, `project_id`), every one answered with the same workspace-wide list spanning four folders. Anything that passed a folder to that endpoint and read the result as one folder was scanning the whole workspace while reporting a folder. `workato_recipe_step_search(folder_ids)`, `workato_recipe_callers`' folder scopes, `workato_search_recipes(folder_id)` and `workato_recipe_save_with_dependents(scan_folder_id)` now resolve folder membership through `GET /dependency_graphs.json?asset_type=recipe&folder_id=<fid>`, the only exact membership list Workato offers, or by filtering the walked items client-side on their own `folder_id`, and report which under `coverage` / `scope`. Membership is exact, so a subfolder needs its own id from `workato_list_folders`.
- **Scope and an input query on `workato_recipe_step_search`.** `folder_ids` scans exactly those folders, `recipe_ids` reads exactly those recipes and skips the listing entirely, `input_query` with `input_match: substring|regex` keeps only steps whose serialized input matches, and `preview_chars` (default 2000) returns an oversized input as `input_preview` plus `input_chars` instead of the whole block. The response now carries `scope` and `coverage`, so a filled `limit`, `max_pages` or `max_recipes` is visible as an unfinished scan.
- **`workato_recipe_step_search` no longer reports a failed page as the end of the list.** A non-first list page that returned an HTTP error fell through with an empty item array, ending the walk as though the workspace held nothing more, while `pages_scanned` still counted it. A mid-walk failure now sets `incomplete` with the reason.

### Caller discovery

- **`workato_recipe_callers`**: who calls a recipe, with the evidence labelled. A long session found 2 of 5 callers in three folders after 68 calls, because the only discovery path was a folder scan that read page 1 and stopped. This combines three sources: Workato's own dependency graph (`GET /dependency_graphs/<id>.json?asset_type=recipe`, the Flow to Flow edges behind the Operations hub dependency page, one request and workspace-wide), a paged code scan that matches `call_recipe` / `call_recipe_async` `input.flow_id` and is the only source that can name the calling step, and `calling_recipe_id` off recent jobs, which is observed execution history and is labelled as such. Scope is the recipe's own folder by default, or `folder_ids`, a project, or the whole workspace; folder membership comes from the dependency-graph folder listing or a client-side `folder_id` filter, because the asset search ignores the parameter, and the candidate listing is narrowed server-side with `adapters=workato_recipe_function`. Also returns callees, connections, lookup tables and workflow-app pages from the graph, and optionally the transitive caller closure with any call cycle and the indirect callers with their depth.
- **Caller discovery says what it did not see.** `unresolved_dynamic_targets` lists call steps whose `flow_id` is a datapill or a formula, which no static scan can resolve; `failed_reads` names the recipes it could not open and why (deleted, moved, no permission); `scope` reports the folders listed, pages walked, recipes read and whether every listing reached its end; and `completeness` is `partial` with reasons whenever any of that applies. A list of N callers is never presented as proof that only N exist. A caller's `running` state is `null`, not `false`, when neither the listing nor the graph saw the recipe.
- A version-aware caller index, held in memory and in `chrome.storage.session`, keyed on the recipe list's `updated_at`. A repeated call re-reads only the recipes that actually changed, reuses anything this session already pulled from the snapshot cache (reported as `freshness.snapshot_reads`), and `refresh: true` forces a full re-read.
- **`workato_recipe_save_with_dependents` discovers callers instead of scanning one page of one folder.** `scan_folder_id` now runs `workato_recipe_callers` (one call, not one recipe pull per candidate) and keeps working unchanged; `scan_folder_ids`, `scan_project_id` and `scan_scope` widen the search to several folders, a project or the workspace. When discovery comes back partial, the save says so in its response instead of presenting the dependent list as complete.
- The `active_dependent_recipes_count` cross-check now fires on a refused dependent stop as well as on a failed save, and compares Workato's count against the callers this call actually discovered and stopped, naming the gap as a warning.

### Connection health and start diagnosis

- **`workato_recipe_connections`**: the connections one recipe is bound to, and whether they can still authenticate. Workato publishes no per-recipe connection endpoint, so the tool reads the recipe's `config` bindings, then each bound connection, then `/integrations/meta` for the providers that carry no `account_id`, and returns one entry per binding with `status` of `ok`, `lost`, `missing`, `not_required` or `unknown`, plus a verdict `{healthy, blocking, actions}`. `blocking` is `{provider, connection_id, status, reason}` and the actions are phrased the way the skill asks for them: a broken connection is named by id to re-authorize, never replaced by a request for a new one, and a provider whose adapter needs no connection is reported as `not_required` rather than as a hole. A `config` entry whose provider no step uses is reported as `unused`, left-over binding rather than a break, and never blocks. `healthy` is false on `unknown` too, because a diagnostic gap is not evidence of health. Credentials and the provider input bag never leave the tool: the response passes through `stripConnectionSecrets` and then a field whitelist.
- **A failed start now says why.** `POST start.json` answers `202 {"status":"enqueued"}` whether or not the recipe can start, and `/recipes/<id>.json` afterwards records nothing: no `stop_reason`, no `last_actionable_error`, no `requirements_errors`. The reason lives only in `/web_api/recipes/<id>/state.json`, which the editor polls right after the Start click. `workato_start_recipe` now reads it when a `wait: true` window ends without the state flipping, and returns an ERROR carrying `start_error` `{state, code_errors, config_errors, param_errors, requirements_errors, message}` that names the offending line and field. `config_errors` is normalized to `[{line_number, field, value, message}]` from either serialization Workato uses (positional arrays on later reads, objects on the read right after activation), and a config error about `account_id` also attaches a compact connection summary, so a disconnected connector is diagnosed in the same call instead of a browser hunt. `diagnosis_error` appears when the diagnostic read itself failed.
- **`workato_start_recipe` and `workato_stop_recipe` report how far the call got.** Every response carries `outcome`: `state_reached` when the recipe reports the state that was asked for, `accepted` when Workato took the request and the end state is NOT verified, `failed` when Workato refused to activate the recipe. A start that never reached running used to come back as a success with `state_flipped: false` buried in the JSON, which reads as restored to anything checking `isError` alone. `workato_stop_recipe` never reads `state.json`, so a stale start error is not reported as a stop failure.
- `workato_recipe_status` returns `activation` `{state, error_message?, config_errors?}`: the last activation attempt as Workato recorded it, or `activation_unavailable` when that read fails. No error there means no failed attempt on record, which is not the same as "this recipe can start"; there is no pre-start validation endpoint (`validate.json` and `ready.json` are both 404).

### Durable, recoverable operations

- **`workato_operation_status`**: a save that times out no longer loses the operation. `workato_recipe_save_with_dependents` stops several production callers, saves one callable and puts them back; each of those is a nested bridge call with a 120 s ceiling, and until now the list of what had been stopped lived only in a closure that died with the request. The whole sequence is now journalled to disk (one JSON file per operation in the bridge state directory, atomic tmp plus rename writes, 200 records or 7 days, `WORKATOMCP_OPERATIONS_DIR` to override), the phase is written BEFORE the call it describes so an interrupted call still leaves a trace, and every save response carries an `operation_id`. The tool reads that journal back locally, with no browser round trip: context, every affected recipe with the running state and version it had BEFORE the operation, phases with timestamps, the save outcome, and the reason anything was left stopped. `list: true` shows the recent operations, `refresh: true` adds one live `workato_recipe_status` per affected recipe plus a drift list.
- **`workato_operation_status(resume: true)` finishes an interrupted restore.** It re-reads every affected recipe, restarts ONLY the ones that were running before the operation and only when the callee's saved version is usable and the connections are healthy, leaves recipes that were already stopped stopped, and lists exact ids and reasons for anything it will not do. When the save's own outcome is unknown it is re-issued under the `expected_base_version_no` the journal recorded before the stops, so Workato answers `already_applied` instead of creating a second version, and refuses outright if somebody else saved in between. It never rolls back over another editor's version. A code tree passed inline cannot be re-issued (the journal stores a path or a hash, never a tree), which the response says in those words.
- **`workato_recipe_save_with_dependents(async: true)`** returns `{operation_id, phase}` immediately and keeps running in the bridge. The default stays synchronous, and its response carries the same `operation_id`.
- **A connection preflight before anything is stopped.** `workato_recipe_save_with_dependents` now calls `workato_recipe_connections` for the callee and for every running caller it is about to restart. A callee whose connections are broken is still SAVED, because a disconnected connector must not make a recipe uneditable, but it is not restarted and no caller is restarted against it; the response names the connection ids and the reasons. A caller whose own connections are broken is left stopped with its reason rather than started into a failure. A health read that FAILS is treated as a diagnostic gap and does not block a restart. `preflight_connections: false` skips the checks.
- **`workato_recipe_save_with_dependents` reads the lifecycle outcome instead of assuming it.** A restart is counted only when the start reports `state_reached`; an `accepted` start gets exactly one `workato_recipe_status` re-check and is then reported as FAILED, with the caller left stopped and named. The old helper checked `isError` alone, so a start that never reached running came back as "stopped and restored".
- **A persisted-but-broken save is no longer described as "nothing changed".** `persisted_invalid` (a new version exists, Workato reports validation errors) and `persisted_incomplete` (a new version exists, Workato dropped input keys) are both reported with the version number and the errors or dropped paths, and neither restarts callers against the callee. Only a save that genuinely created no version restores the callers. `isError` is true for `persisted_incomplete` and false for `persisted_invalid`.
- **The save carries a version lock taken before the stops.** `expected_base_version_no` now defaults to the callee's own version read during the preflight, so a retry after a timeout re-sends the same base version and cannot create a duplicate. An explicit value still wins. This is a behaviour change: a save that previously went through while somebody else had saved in between is now refused.
- **Dependents are revalidated after the stops.** When discovery was used and something was actually stopped, `workato_recipe_callers` runs once more; a caller that appeared in the meantime is stopped, restored with the rest, and reported as `late_discovered_caller_ids` rather than silently blocking the save.
- **An interrupted nested call is reported as interrupted, not as a generic failure.** The response names the phase, the exact recipe ids whose state is unknown, and the `operation_id` to poll or resume; nothing is rolled back blindly on a transport that just failed to answer. The old outer catch always called `restoreAll`.
- The save payload gains `operation_id`, `save_classification`, `expected_base_version_no`, `dropped`, `callee_connections_healthy`, `callee_connections_reason`, `late_discovered_caller_ids`, `discovery_completeness` and `discovery_reasons`; each `dependents[]` entry gains `restart_outcome`, `blocked_reason`, `connections_healthy` and `discovered_late`.

### Test execution

- **`workato_test_recipe`**: run a recipe's Test, with trigger input, from the tool layer. Until now the only way to feed an event into a recipe was to build a throwaway recipe and click Test in the browser. The mode is read from the trigger rather than promised for everything: a `workato_recipe_function` trigger takes `trigger_input` (sent as `trigger_event.parameters`, checked against the trigger's declared parameters first, so a typo is refused instead of arriving as an empty pill), a `clock` trigger runs immediately and accepts no input, a webhook or `workato_pub_sub` trigger arms a test that waits for a real event (`action: 'stop'` ends it), and any other trigger is refused before a request is sent. Workato's response carries no job id, so the tool records the test jobs that already exist, sends the PUT, and polls the test-job list; a wait that runs out returns status `pending` with the elapsed time and the job as it actually stands, never a guessed outcome. The recipe is not started and stays stopped afterwards with `stop_reason: test_run_stop`. `action: 'status'` reports `flow.testing` and the newest test job.
- **Testing is execution, so it is gated like one.** A test runs the recipe's real steps, so `allow_writes: true` is required whenever the recipe binds a connection-backed provider (a `config` entry carrying `account_id`, or a step provider the config does not describe at all). The refusal names the providers and happens before any HTTP. A recipe whose providers are all connectionless (logger, Variables, Event Streams, Scheduler, Python) runs without the flag, which is what makes a probe recipe cheap to run. The gate reads only the recipe under test: a connectionless recipe that calls a callee which does touch a connection is not caught.
- **Publishing to an Event Streams topic has no API, and the tools now say so.** The topics UI has no publish action and `POST /web_api/pub_sub/topics/<id>/messages.json` is a 404, so no `workato_publish_message` tool was added. The supported path, documented on `workato_test_recipe` and in the skill, is to test-run a recipe with a `workato_pub_sub` / `publish_to_topic` step whose input is `{topic_id, message}` plus a matching `extended_input_schema`. `workato_call_action` now states the matching limit: its endpoint needs a real connection id, an adapter name is rejected, so a connectionless step can only be executed inside a recipe test. `poll_now` is not an action either; the returned note points at `workato_api_request` with `PUT /recipes/<id>/poll_now.json {"id":<id>}`.

### Session context, routing and file locks

- **`workato_session_context`**: the cheap answer to "where would this call land?": tab, host, workspace, environment, user, from `/web_api/auth_user.json` and nothing else. `workato_whoami` returns roles, teams, membership and every available environment behind a debugger attach; this reads the five fields routing depends on through the ordinary script dispatch and caches them per tab for 60 s (`max_age_ms` up to 600000, `refresh` to bypass), dropping the entry the moment the tab navigates or closes.
- **Every successful `workato_*` response says where it ran.** One extra text block, `{"context":{"tab_id":..,"host":..,"workspace_id":..,"workspace_name":..,"environment":..}}`, under 200 bytes, with the routed profile added by the bridge, always last so existing parsers that read the first block are unaffected. Workato resolves the workspace from the tab's own session, so until now nothing in a response distinguished "recipe 123 in prod" from "recipe 123 in the sandbox". Resolving the context can never fail a call: when it cannot be read, the block is simply absent.
- **A pinned session pins the workspace, not just the tab.** `workato_switch_profile(profile, tabId)` now reads that tab's workspace and environment once and keeps the whole tuple (profile, tab, host, workspace, environment, pinned_at); `workato_list_profiles` returns it as `session_context` along with a `routing_note` about how calls are routed. Every later Workato call, top-level and nested, carries the pinned tab and an `expected_context`, so a multi-step operation can no longer read one tab and write another.
- **Writes verify the workspace before they act.** `workato_ui_save_recipe_code`, start/stop, non-GET `workato_api_request`, delete/rename/move/copy recipe, the nine lookup-table writes, the nine data-table writes and the four workflow-app writes (page save, widget patch, page create, page delete) check the target tab against the expected context and refuse with `ContextMismatch`, naming expected and actual, before anything is fetched or written. They already refused a stale tab id; they could still write into the wrong workspace through a valid tab.
- **A pinned profile is never routed around.** A failed call to a pinned profile is reported, naming that profile and the connected ones, instead of being re-sent to another profile or to the legacy native-messaging host. With no profile pinned the bridge default is still used, but a failure there is reported too. The stdio host stays reachable only when no Chrome profile is connected at all, and the response says that is what happened.
- **A profile that reconnects is re-checked.** The registry now carries a generation counter; a pinned session re-reads its tab's context after any connect or disconnect and refuses the call with `ContextChanged` when the workspace or environment moved.
- `resolveTabId` throws when an explicit tab is gone or is no longer a logged-in Workato app tab, instead of silently falling through to whatever other Workato tab is open. That fallthrough is how a save aimed at a closed pinned tab could land in another workspace. `findWorkatoTab` also takes a `windowId` now, so window-scoped resolution lives in the dispatcher rather than inside one tool.
- **Recipe files record where they came from.** `workato_pull_recipe(out_file)` writes an `origin` block (pulled_at, profile, tab, host, workspace id and name, environment, folder). The push reads it back: a save into a different workspace is refused unless `allow_context_mismatch: true`.
- **A file save defaults to the version it was pulled from.** `workato_ui_save_recipe_code(code_path)` sets `expected_base_version_no` from the file's `version_no` when the caller gives none, so a file edited yesterday can no longer overwrite today's version by omission. `ignore_file_version: true` is the deliberate override. A file whose `recipe_id` is not the recipe being saved is refused outright rather than written under the wrong id.

### Transport and auto-file

- **A generic `out_file` and an auto-file mode for large read results.** Only `workato_pull_recipe`, `workato_lcap_page_get`, `workato_api_request` and `workato_adapter_meta` had a way out of the context: everything else returned its whole payload, so a broad job trace or step search was paid for in tokens. Every Workato read tool (jobs, traces, recipe and step search, callers, grep, connections, version diff, recipe status, apps, pick lists, queries, actions, lookup and data tables) plus `chrome_screenshot` now serves `out_file`, `auto_file` and `auto_file_threshold_chars`, injected into the served schemas rather than repeated per tool. With `out_file` the full text goes to that path; with `auto_file` (on by default for the read tools, off for `chrome_screenshot`) it goes to a per-session file under the temp directory once the result passes 60,000 characters. What comes back is a summary: `saved_to`, `bytes`, `content_type`, `version_no`, the top-level keys, the item count of each array, and any truncation flag the payload carried (`truncated`, `truncated_fields`, `total_bytes`, `total_items`, `total_count`, `has_more`, `next_page`, `next_cursor`, `limit`, `coverage`, `search_mode`, `warning`), copied verbatim so a partial result cannot read as complete. Nothing is written for a failed call, and the four tools that already own an `out_file` hook keep their exact behaviour.
- **`chrome_screenshot(out_file)`** writes the decoded image bytes to a path of your choosing, unlike `savePng`, which can only reach Chrome's Downloads folder. It writes the compressed JPEG the image block carries; the image still comes back inline unless `no_inline` is set.
- **A screenshot is returned as an image, not as base64 inside a text block.** `storeBase64: true` used to serialize the whole capture into JSON text: expensive to carry, and no client renders it. `chrome_screenshot` and `chrome_computer` (`screenshot` and `zoom`) now return an MCP `image` block plus a small metadata block (tabId, url, name, width, height, mimeType, bytes, fileSaved, fullPath); the base64 payload never appears in text. The record-replay screenshot node and action handler read the image block, and `chrome_computer` scales clicks from the compressed image the client actually sees.
- **`storeBase64` and `savePng` compose.** `storeBase64: true` returned before the save branch, so a caller who asked for both got only the image and a `fileSaved: false` that was not true of the request. The schema also claimed `fullPage` defaults to true while the handler defaults it to false, and implied the two output flags were independent when they were not. Both descriptions now match the code.

### Server identity, CI and tooling

- **`workato_bridge_info`**: which build is actually answering. Runs entirely in the local bridge, so it still answers when the extension is disconnected, and returns `bridge_version`, `shared_version`, `tool_count`, `schema_revision` (a stable 12-hex hash of the served catalogue, canonicalized so array order and key order cannot move it), `connected_profiles`, `session_context`, `default_profile`, `node_version` and `platform`, plus `versions_read` naming the manifest each version came from. A missing tool or a parameter rejected as unknown is usually a bridge or an unpacked extension that was not reloaded after an upgrade; comparing one `schema_revision` against a working session's names that instead of guessing at it.
- **The MCP handshake identifies the real build.** The server reports `WorkatoMCP` and the bridge version read from the `package.json` that ships in `dist`, instead of the inherited `ChromeMcpServer 1.0.0`, which matched no release of anything. An unreadable manifest reports `0.0.0-unknown` rather than a version anyone should trust.
- **Server instructions.** The handshake now carries a task-to-tool table under 1500 bytes: one field to change goes to `workato_recipe_set_input_path`, several edits or any structural change to `workato_recipe_apply`, finding a field to `workato_recipe_grep`, a job to `workato_job_trace` with `paths`, jobs to `workato_list_jobs` with a date range or `match`, callers to `workato_recipe_callers`, connection health to `workato_recipe_connections`, a pre-save check to `workato_recipe_validate`, a long save to `workato_recipe_save_with_dependents` then `workato_operation_status`, a fixture to `workato_test_recipe`, the target workspace to `workato_session_context`, the running build to `workato_bridge_info`. A client with lazy tool discovery sees tool NAMES before it sees any schema, so the guidance has to live where it is read first.
- **Tests gate CI.** `.github/workflows/ci.yml` runs the extension vitest suite and the bridge jest suite after Lint. Bridge coverage thresholds stay off in CI: a red test should fail the build, a percentage should not.
- **A post-build bundle check.** `pnpm --filter workatomcp-extension check:bundle` (chained after `wxt build`, so `pnpm build` and `pnpm build:extension` both run it) fails when the built background script contains a `function _<name>InPage` helper or an `_asyncToGenerator` wrapper around an in-page function, for any name other than the two service-worker helpers that never reach a page. The es2015 target rewrites an `async` in-page function into a pair, only half of which crosses into the tab; that cost three smoke tests to find the first time and is now caught at build.
- **A tool-name drift guard.** A bridge jest test asserts that every literal in `WORKATO_RECIPE_MUTATOR_TOOLS`, `READ_TOOLS` and the other bridge-side name sets, and every `'workato_*'` string in the MCP sources, exists in `TOOL_NAMES`. A name that drifts used to fall through to the extension and come back as "Tool X not found" at runtime. A genuine provider literal (`workato_pub_sub`, `workato_recipe_function`, `workato_variable`) is allowlisted separately.
- **A description budget test.** Every served tool description is asserted under 2048 bytes, and no Workato tool or property description may contain an em-dash or en-dash. `workato_apps_list` was 2245 bytes, over the 2 KB a client allows for one tool; it is now 1947 with every load-bearing rule kept (no connection means stop and ask, Workato's own connectors are named nothing like they are called, there is no catalogue of the standard connectors). Seventy dashes and twelve en-dash numeric ranges were replaced across the Workato catalogue, so `10000-110000` uses the same hyphen everywhere.

## bridge 1.5.0 · shared 1.2.0 (2026-08-26)

### Added

- **`workato_apps_list`**: which apps this workspace can build a step with, and their TECHNICAL adapter names. `workato_adapter_meta` describes one connector in full but only once its name is known, and the name is exactly what cannot be guessed for a custom connector (`netsuite_rest_connector_5105163_1745592003`). Merges connections, the adapters already used by recipes here, this workspace's SDK connectors and Workato's certified catalogue into one list, tagging each app with where it came from and sorting the immediately usable ones first. The response states the limit rather than hiding it: Workato publishes no catalogue of its standard connectors — the recipe editor compiles that list into its own bundle and makes no request for it — so absence from this list is not proof an app does not exist, and the way to test a guessed name is the array form of `workato_adapter_meta`.
- **`workato_recipe_step_search`**: real steps from real recipes, as templates. Meta says what a field is called; it cannot say what a working value looks like, and that only exists in the recipes already running in the workspace. Scans the recipe list (each item already carries `trigger_application` and `action_applications`, so candidates are found without opening them), reads the matches and walks the tree at any depth, so a step nested inside an if / repeat_each / try block is found too. Zero results is reported as a normal answer with the scan size, not as an error.
- **`workato_apps_list` carries Workato's own built-in connectors**, whose display name and adapter name share almost nothing: HTTP is `rest`, Workato Event Streams is `workato_pub_sub`, Scheduler is `clock`, Python snippets is `py_eval`, Workflow apps is `workato_workflow_task`. Guessing from the display name returns an empty meta document, indistinguishable from "no such app": `workato_event_streams` and `event_streams` both resolve to nothing. Only the list of NAMES is fixed in the tool; title, aliases, categories and connection_required are read live from `/integrations/meta` on every call, so a rename shows up immediately and no stale copy is shipped. Verified live: "event stream", "pub/sub", "HTTP", "scheduler", "python", "approval", "lookup table" and "csv" each resolve to exactly one right adapter.
- **`workato_pick_list`**: resolve a DYNAMIC pick list against a real connection. `workato_adapter_meta` returns a static select's values inline, but when a field's `pick_list` is a string the values are not in the meta document at all: they are the customer's own Salesforce objects, NetSuite record types, Slack channels, fetched per connection. This was the last thing standing between "the agent knows the field" and "the agent can fill the field". Found by capturing the editor: `POST /connections/<id>/pick_list.json`, whose body is the field definition itself. Verified live: salesforce `all_sobjects` answers with 2567 pairs, and the parameterised `sobject_field_values_list` answers Hot/Warm/Cold for Account.Rating. Two traps carried into the tool: the response is label-FIRST like every other Workato list, and a parameterised list needs its params EVALUATED, because the field shows them as formulas (the value appears wrapped in quotes) and the quoted form fails with `bad URI (is not URI?)`. Quotes copied by mistake are stripped and reported.
- **No connection is a stop-and-ask, not a workaround.** These tools deliberately cannot create a connection: it means handing over the customer's credentials. `workato_apps_list` and the skill now say to raise it before writing the step, because a step needs its provider's `account_id` in the recipe `config` and that id does not exist until the connection does. An app with no `connection` source, or one whose `authorization_status` is not `success` (`connection_lost` reads as working right up until the recipe runs), is a blocker; a `builtin` with `connection_required: false` is not.
- `dynamicPickListSelection` is documented in `code-tree.md`: a field fed by a dynamic pick list is written twice, in `input` and in `dynamicPickListSelection` under the same name. Writing only `input` saves cleanly and leaves the editor showing an empty picker.
- `skills/workato-recipes/discovering-connectors.md`: the ladder from "the recipe should send an email" to a step that works, with no example to copy — finding the adapter name, listing operations, reading an operation's real field surface, and what `connection_required` means for the recipe `config`.

### Fixed

- **`workato_adapter_meta` no longer drops the parts of a field that decide whether the step works.** The slim view kept `control_type: "select"` but threw away the values behind it. Workato stores pick lists label-first, so `email_type` accepts `"html"` and not the `"HTML"` the UI shows — and takes the wrong string silently. Fields now carry `options` (value and label), `default`, `properties` for the item fields of an object or array, and `toggle_field` for the alternative form of a field that accepts either shape. `field_grep` searches nested names too. Found by taking a connector this workspace had never used and checking what an agent would actually have written.
- `workato_adapter_meta` returns the adapter's own `title`, `aliases` and `categories`, which is what confirms a guessed name landed on the right app, and `connection_required` — false means the connector needs no connection at all and its `config` entry carries no `account_id`. Verified against a live recipe whose config holds `email` without one beside `salesforce` with one.

### Fixed

- **`out_file` wrote a truncated document and reported it as whole.** On `workato_api_request` the native-server asked for the body with `max_bytes: 200_000`, which is exactly where the extension clamps, so a larger response reached disk cut short under a `bytes_written` count that read as complete. `workato_adapter_meta(out_file)` was worse: raw mode caps at 20k chars and its own note tells the caller to use `out_file`, which then wrote the same 20k. ### Changed

## bridge 1.4.2 · shared 1.1.2 (2026-08-26)

### Changed

- **The merged-row check is a warning, not a refusal.** Smoke-testing 1.4.1 against a live page disproved the assumption behind it: two full-width text widgets moved onto one row do not overlap. The renderer stacks them (`top: 0px` then `top: 32px`), the container keeps its height, and the container after it keeps its own `top`.
